# Платёжный сервис Med-Service (CLI-прототип)

Это консольный прототип (CLI) платёжного сервиса для клиники. Прототип эмулирует работу банковского шлюза, поддерживает двухэтапную оплату (создание + подтверждение), строгую валидацию (правила V-1…V-9), идемпотентность, защиту от брутфорса и ведение аудита.

## ⚙️ Требования
- Установленный Python 3.8 или выше.
- Дополнительные библиотеки не требуются (используется только стандартная библиотека Python, включая `decimal` для точных денежных расчётов).

## 📁 Структура проекта (папка `04_прототип`)
- `05_app.py` — основной файл CLI-приложения (точка входа).
- `gateway_emulator.py` — модуль детерминированной эмуляции банковского шлюза.
- `payment.json` — базовый пример входящего запроса на оплату.
- `01_данные/recipients.csv` — справочник получателей платежей (оплата доступна только для `status = ACTIVE`).
- `payments_out.csv` — база данных (журнал созданных платежей и их статусов). Создаётся и обновляется автоматически.
- `events.log` — внутренний журнал аудита (история переходов между статусами в часовом поясе МСК `UTC+3`). Создаётся автоматически.
- `gateway.log` — журнал обращений к банковскому шлюзу (используется для контроля количества фактических вызовов банка, в т.ч. в тесте идемпотентности `T1-4`).
- `tokens.json` — хранилище активных одноразовых токенов подтверждения с контролем TTL (600 сек) и счётчиком попыток ввода.
- `тесты/` — директория с артефактами тестирования:
  - входные запросы: `T1-1.json` … `T1-6.json`;
  - контрольные выгрузки БД: `T1-1.csv` … `T1-6.csv`, `1-4 final.csv`;
  - скриншоты результатов прогона: `тест 1-1.png` … `тест 1-5.png`, `тест 1-4 ошибка.png`, `тест 1-4 финал.png`, `T1-6.png`.

## 🚀 Как запускать

Перед запуском команд перейдите в директорию прототипа:
`cd 04_прототип`

Скрипт поддерживает 4 команды: `create`, `confirm`, `status` и `cancel`.

### 1. Создание платежа (create)
Проверяет входной JSON по правилам `V-1...V-9`.
- Если валидация **не пройдена**, запись в `payments_out.csv` **не создаётся**, возвращается ошибка валидации.
- Если валидация успешна, создаётся платёж в статусе `CREATED` и генерируется одноразовый `confirm_token` (срок действия `TTL = 600` сек).
- **Идемпотентность:** при повторном вызове с тем же `idempotency_key` дубликат не создаётся — возвращается текущий статус платежа, а для статуса `CREATED` — действующий токен и актуальный остаток времени `expires_in`.

**Команда:**
`python 05_app.py create payment.json idem_001`
*(Либо запуск конкретного тест-кейса: `python 05_app.py create тесты/T1-1.json idem_t1_1`)*

### 2. Подтверждение платежа (confirm)
Проверяет одноразовый токен подтверждения и отправляет запрос в банковский шлюз:
- **Контроль TTL:** если с момента создания прошло более 600 секунд, платёж переходит в статус `DECLINED` (`TOKEN_EXPIRED`, код выхода `410`).
- **Защита от перебора (Brute-force):** даётся максимум 3 попытки ввода токена. На 1-й и 2-й ошибке возвращается код `422` и остаток попыток. На 3-й ошибке токен аннулируется, платёж переходит в `DECLINED` (`INVALID_CONFIRM_TOKEN`, код выхода `410`).
- **Идемпотентность и однократный вызов шлюза (сценарий T1-4):** после верного ввода токена он удаляется из `tokens.json`. При любом повторном вызове `confirm` для уже обработанного платежа (`SUCCESS`, `PENDING` или банковский `DECLINED`) шлюз повторно **не вызывается** (в `gateway.log` и `events.log` не появляется дублирующих записей), а клиенту возвращается сохранённый результат из базы.

**Команда:**
`python 05_app.py confirm <payment_id> <confirm_token>`
*Пример:* `python 05_app.py confirm pay_demo_1a2b3c a1b2c3`

### 3. Проверка статуса (status)
Возвращает текущий статус платежа, код ошибки (если есть) и полную историю переходов (`history`) из журнала аудита `events.log`.

**Команда:**
`python 05_app.py status <payment_id>`

### 4. Отмена платежа (cancel)
Переводит платёж в статус `CANCELED` и аннулирует токен подтверждения.
- **Безопасность при таймаутах:** отмена разрешена **только** для платежей в статусе `CREATED` (пока запрос ещё не отправлялся в банк).
- Если платёж находится в статусе `PENDING` (таймаут шлюза), отмена **запрещена** (`INVALID_STATE`, код выхода `409`) до сверки финального статуса с банком, чтобы исключить ситуацию, когда банк списал средства, а платёж был отменён локально.
- Для финальных статусов (`SUCCESS`, `DECLINED`, `CANCELED`) отмена также запрещена (`409`).

**Команда:**
`python 05_app.py cancel <payment_id>`

## 🔄 Отличия CLI-прототипа от целевого REST API

В рамках прототипа консольный интерфейс моделирует поведение проектируемого HTTP API (описанного в `06_openapi.yaml`):
1. **Передача `Idempotency-Key`:** в целевом REST API передаётся в HTTP-заголовке `Idempotency-Key`, а в CLI — третьим аргументом команды `create`.
2. **Хранение данных и уникальность:** в целевой архитектуре уникальность `idempotency_key` и пары `(order_id, recipient)` обеспечивается `UNIQUE`-индексами СУБД и Redis (для TTL токенов). В CLI-прототипе это реализовано программной проверкой по `payments_out.csv` и `tokens.json`.
3. **Коды завершения (Exit Codes):** вместо HTTP-статусов CLI возвращает коды завершения процесса (`sys.exit`), соответствующие кодам ответа сервиса:
   - `0` — успешное выполнение (аналог HTTP `200 OK` / `201 Created`);
   - `1` / `400` — некорректный синтаксис команды или невалидный JSON (`BAD_REQUEST`);
   - `402` — отказ банковского шлюза (`INSUFFICIENT_FUNDS`, `CARD_DECLINED`);
   - `404` — платёж или активный получатель не найден (`PAYMENT_NOT_FOUND`, `RECIPIENT_NOT_FOUND`);
   - `409` — конфликт состояния или дубликат заказа (`DUPLICATE_ORDER`, `INVALID_STATE`);
   - `410` — токен истёк или исчерпан лимит из 3 попыток (`TOKEN_EXPIRED`, `INVALID_CONFIRM_TOKEN`);
   - `422` — ошибка валидации полей запроса или неверный токен при оставшихся попытках (`VALIDATION_ERROR`, `INVALID_CONFIRM_TOKEN`);
   - `504` — таймаут ожидания ответа от банковского шлюза (`TIMEOUT` -> статус `PENDING`).

## 🧪 Тестирование различных сценариев шлюза

Эмулятор `gateway_emulator.py` выбирает результат детерминированно на основе SHA-256 хэша от `order_id`. Чтобы гарантированно воспроизвести нужный сценарий, укажите соответствующий `order_id` в `payment.json` (или используйте файлы из папки `тесты/`):

- 🟢 **Успех (`SUCCESS`):** `"order_id": "ord_1001"` (также подходят `"ord_1008"`, `"ord_1009"`)
- 🔴 **Недостаточно средств (`DECLINED` / `INSUFFICIENT_FUNDS`):** `"order_id": "ord_1002"`
- 🔴 **Карта отклонена (`DECLINED` / `CARD_DECLINED`):** `"order_id": "ord_1007"`
- 🟡 **Таймаут шлюза (`TIMEOUT` -> статус `PENDING`):** `"order_id": "ord_1006_timeout_3"`
